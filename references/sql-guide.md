# SQL 直查数据集指南（通用版）

当卡片粒度不够时（如"单月指标""卡片没拆的维度"），用 SQL 直查数据集补充。

## 何时切换到 SQL 模式

| 卡片 preview 够用 | 必须切 SQL 模式 |
|---|---|
| 卡片已有对应粒度（累计/按省/按片区） | 卡片没有对应粒度（如"单月客单价"） |
| 看板 KPI 卡/统计表/趋势卡直接覆盖 | 卡片没拆的维度（如拆店数、自定义时间段） |
| 问数/归因/异常识别 | 卡片粒度不够，需按日期/字段自由聚合 |

## 用法

```bash
# 1. 探查数据集字段（先用这个，拿到数据集 ID 和字段列表）
guancli ds get <数据集ID> --brief

# 2. 执行聚合查询（核心命令——必须走只读执行器，禁止直接调 guancli ds execute-sql）
python3 references/run_sql.py <数据集ID> 'SELECT ... FROM `数据集名称` WHERE ... GROUP BY ...'
```

`run_sql.py` 是 `guancli ds execute-sql` 的只读包装：强制单条 SELECT/WITH 查询，拦截多语句与写操作关键字。被拦截时说明 SQL 写错了，改写为纯查询即可。搭建向导阶段脚本路径为 `references/scripts/run_sql.py`。

### 示例：查某省份某月单月指标

```bash
python3 references/run_sql.py <数据集ID> '
SELECT
  SUM(`销售额`) AS sales,
  SUM(`门店销售目标`) AS target,
  SUM(`订单总数`) AS orders,
  SUM(`店天总数`) AS store_days,
  SUM(`毛利总额`) AS gross_profit
FROM `数据集名称`
WHERE `省份` = "安徽"
  AND YEAR(`日期`) = 2026 AND MONTH(`日期`) = 3
'
```

然后现算派生指标：
- 完成率 = sales ÷ target
- 客单价 = sales ÷ orders
- 日均店单数 = orders ÷ store_days
- 单店日均销售额 = sales ÷ store_days
- 毛利率 = gross_profit ÷ sales

## ⚠️ 已踩过的坑（必须规避）

| 坑 | 现象 | 规避 |
|---|---|---|
| **SQL 别名不能用中文** | `AS 销售额` 报 `Syntax error near '销'` | 别名一律用英文（sales/target/orders） |
| **金额字段是"元"** | SQL 返回原始元值（如 8400658.67） | 查询后 ÷10000 转"万"再展示 |
| **结果是明细行** | 单日数据，需自己聚合 | 必须用 SUM/COUNT 聚合，禁止直接 LIMIT 截断当汇总 |
| **日期是 DATE 类型** | 不能直接 `=` 匹配月份 | 用 YEAR(`日期`)/MONTH(`日期`) 切月份，或 `日期` BETWEEN |
| **交叉验证** | SQL 结果可能与卡片有出入 | 先与卡片 preview 交叉验证，误差 >2% 时先自查 SQL 再回答 |

## 🔴 口径一致性红线（SQL 模式核心约束）

SQL 取数是自由查询，**自由意味着口径可能和看板不一致**。这是 SQL 模式最大的风险，必须严守以下规则：

### 1. 口径一致性校验（每次 SQL 取数必做）
- SQL 算出来的指标，必须与看板同名卡片**交叉验证**
- 误差 ≤2% 时，可直接用看板口径
- 误差 >2% 时，**必须声明差异**，让用户知道"这个数跟看板上的口径不同"

### 2. 模糊口径声明（与看板不一致时必须执行）
当 SQL 算的口径与看板口径不一致时，回答前必须明确声明：
> "该指标由 SQL 基于数据集《XX》计算，口径为 XX；与看板《XX》上的口径 XX 存在差异（差异 XX%），请注意区分。"

**绝不隐瞒口径差异**——这是 SQL 模式的第一红线。

### 3. 冗余字段红线（禁止乱引用）
底层数据集有很多字段与当前分析场景无关。**引用前必须确认该字段是否在看板卡片中被使用**：
- ✅ 看板卡片用到的字段（如 `销售额`/`门店销售目标`/`订单总数`/`店天总数`/`毛利总额`）→ 可引用
- ❌ 看板卡片未用到的字段（如 `门店装修风格`/`格斗数`/`销售厅面积` 等）→ **禁止引用**，除非用户明确要求
- ⚠️ 字段名相似但口径不同的（如 `店外业绩` vs `店外业绩占比` vs `门店团购销售额`）→ 先确认业务含义，再引用

### 4. 复杂口径必须追溯来源
当 SQL 计算复杂口径时（如"单店日均销售额 = 销售额 ÷ 店天总数"），必须：
1. 在回答中标注"该指标由 SQL 计算，公式 = 销售额 ÷ 店天总数"
2. 与看板同名卡片交叉验证
3. 若看板卡片也计算了该指标，以看板口径为准；若看板没有，以 SQL 口径为准但声明差异

## 数据红线（SQL 模式追加）

- SQL 结果必须与卡片 preview 交叉验证，误差 >2% 时先自查取数再回答
- **口径一致性校验**：SQL 算出来的指标必须与看板同名卡片交叉验证；误差 >2% 时必须声明差异，绝不隐瞒
- **模糊口径声明**：SQL 口径与看板口径不一致时，回答前必须明确声明数据来源和计算口径
- **冗余字段红线**：底层数据集字段 ≠ 看板口径字段；引用前必须确认该字段是否在看板卡片中被使用，未使用的字段禁止引用，防止口径混淆
- **复杂口径追溯**：SQL 计算复杂口径时，必须在回答中标注计算公式的来源
- 金额字段统一 ÷10000 转"万"后再展示给用户
- 中文别名是已知的 SQL 解析器陷阱，必须用英文别名
- 数据是明细行（如门店×日期），必须聚合后才能当汇总使用

## 搭建向导接入点

在搭建 data agent 时：
- **第 2 步（资产学习）**：cards-raw.json 已记录每张卡片的数据集 ID，用 `guancli ds get <dsId> --brief` 探查数据集是否有 SQL 直查能力，若有则记入资产目录
- **第 7 步（测试验收）**：若启用 SQL 模式，用 run_sql.py 测试至少 1 个"卡片粒度不够"的查询，验证 SQL 结果与卡片结果交叉闭环
- **第 8 步（固化交付）**：若数据集有 SQL 直查能力，在助手 SKILL.md 中标注"SQL 直查触发条件"，并在 references 中保留 sql-guide.md 与 run_sql.py
