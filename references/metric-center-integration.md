# 指标中心轻量集成方案（2026-09-29）

> 本文件记录"口径确认产物与观远指标中心打通"的集成设计。定位是**轻量集成**，不是指标建设项目——指标的体系化梳理与批量建设由专门的迁移 skill（guandata-metric-migration，持续迭代中）承担，本向导只做三件事：**引用已发布的同口径指标、顺手创建原子指标、对没有权限的用户做一次性推荐**。
>
> 设计前提（已与用户对齐）：
> - 性能不在本项目考虑范围——指标建成后计算在 BI 平台完成，天然优于 agent 本地取数计算；
> - 集成不做重，发现用户有系统性指标建设需求时路由到专项 skill，不在本向导内展开。

---

## 一、为什么值得接：与既有设计的关系

- **趋势锚点**（ROADMAP 生态侧）：纯 RAG text-to-SQL 正被"受治理语义层 + agent"路线取代。指标中心就是观远的语义层——本项目的 metrics.json 是 agent 侧的口径档案，指标中心是平台侧的口径档案，两者对齐是顺着路线走，不是新方向。
- **与设计原则 7 互补**：看板降级为"漂移检测基准 + 呈现模板库"之后，口径的权威源需要一个更稳的落点。指标中心已发布指标正是这个落点——它比看板卡片配置更正式（有状态、有血缘、有权限管理），适合做 metrics.json 的外部锚。
- **已有伏笔**：v4.1 的 agent-ready 评分里"权威标注率（25 分）"已经通过 `guancli metric by-dataset` 查询指标中心，check_pages.py 对查询失败已有"权重重分摊"的降级哲学。本方案是把这条只读通道从"评分信号"升级为"口径引用"。

## 二、触发点与三态探针

**触发点**：第 4 步口径确认完成、`check_metrics.py` 闸门 ❌ 清零之后。快速模式在 L3 后、增量学习在 I3 后同样执行，只处理当期确认的条目。

**探针（第 4 步开头，静默一次）**：判定指标中心对本环境/本账号的可用性，三态：

| 态 | 判定依据 | 处置 |
|---|---|---|
| A 可用 | `metric by-dataset` / `metric search --fuzzy` 正常返回（哪怕 0 条指标） | 进入对齐流程（第三节） |
| B 未开通/无权限 | 接口返回功能未开通或权限类错误（具体错误形态实施时实机确认；确认前统一按"不可用"对待） | 一次性推荐 + 帮助文档链接，继续原流程，**本次搭建不再探针** |
| C 临时失败 | 网络/服务异常 | 沿用"权重重分摊"哲学静默降级，不打扰用户，下次触发再试 |

探针纪律：

- **初判复用第 1 步结果**：check_pages.py 跑过 governed 查询（未带 `--skip-governed`）时，page-check.json 里的 `governed: ok/unavailable` 就是初判，第 4 步只复核不重来。
- **结论落盘**：三态结论写入工作目录（page-check.json 扩展字段或 wizard-state 扩展），断点续建按落盘结论恢复——分支 B 的推荐**全程只出现一次**，不许断点续建后又弹一遍。
- **创建权限不预检**：平台未必提供只读的"能否创建"探测。诚实做法：读权限由探针确认，创建权限在用户选择"要创建"后以第一次 `guanmetric` 写入的实际结果为准——失败按权限类错误提示并退回原流程。

## 三、对齐流程（探针为 A 时）

对 metrics.json 里本期确认的每条指标，做一次匹配：

1. **候选发现**：优先复用 check_pages 的 by-dataset 结果（同数据集已发布指标）；不够的用 `guancli metric search --fuzzy` 补——遵守 guancli 的单批预算纪律（原词 + ≤4 个 synonyms 一次查询，不拆批、不重复搜）。
2. **口径一致性核对**：名称命中（含 metrics.json 的 synonyms）后，用 `metric get --brief` 的 description/dataset/measureFields 与该条 formula 比对。
   - **口径一致 → 分支 A1 直接引用**：该条写入 `governedRef: {metricId, name, status}`；businessKnowledge.md 口径来源标注"指标中心已发布口径"。一致性判断有疑义的，不引用，也不算冲突，标记待确认即可。
   - **口径不一致 → 不是引用，是冲突**：同metrics.json 既有纪律处理——列入拍板组请用户裁决（"指标中心里'退款率'是÷GMV，您看板里是÷收入，以哪个为准？"），**禁止 AI 自行二选一**（红线不破）。用户拍板以看板为准的，该条进入分支 A2 的创建候选。
3. **未命中 → 分支 A2 引导创建**：全部匹配完成后**汇总一次**问用户，不逐条问：

   > "已确认的口径里，有 N 条指标中心还没有收录。您的账号可以在指标中心创建指标——发布上去的好处是口径全公司统一、其他看板和 AI 应用也能复用。要顺手把这几条发布上去吗？（不发布也不影响助手使用）"

   - 用户不发布 → 继续原流程，不问第二次。
   - 用户发布 → **只创建原子指标中可直接创建的**（有明确数据集物理字段 + 标准聚合方式），走 guanmetric 逐条创建并回读校验；成功后回填 governedRef，同 A1。设数量上限（建议 ≤10 条）——超过即提示"数量较多，建议用专门的指标梳理流程批量建设"（路由专项 skill，见第五节）。
   - 复合/派生指标**不在顺手创建范围**（依赖排序、公共维度映射、时间维度配置都是专项工作）——列入提示，路由专项 skill。
4. **分支 B 话术**（探针为 B 时，一次性）：

   > "您的 BI 环境还没有开通指标中心（或当前账号没有指标中心权限）。指标中心是观远的口径统一管理功能——把'销售额怎么算'这类定义固化在平台上，全公司的看板和 AI 助手用同一套口径，回答会更稳。这次搭建不受影响，我们继续。有兴趣可以了解：[指标中心产品简介](https://docs.guandata.com/product/bi/product-introduction)、[指标中心操作流程](https://docs.guandata.com/product/bi/index-center-operation-process)"

## 四、产物改动清单

| 位置 | 改动 | 量级 |
|---|---|---|
| `check_pages.py` | `fetch_governed` 返回值从"指标名集合"扩展为 `{name: {id, status}}`（向后兼容；评分逻辑不变），第 4 步对齐复用该结果省一轮查询 | 小 |
| `metrics.json` schema | 每条可选 `governedRef: {metricId, name, status}`；`check_metrics.py` 加一条校验（结构合法、status=PUBLISHED） | 小 |
| 新脚本 `run_metric.py` | 指标直查薄封装，与 run_sql.py 同构：校验 metricId 在本包 governedRef 白名单内 → `guancli metric query` 只读取数。`scope.py` 白名单同步扩展 metricId 域 | 中（本方案唯一新脚本） |
| `SKILL.md` 第 4 步 | 新增"指标中心对齐"小节：探针三态 + 三分支话术 + 边界；红线区加一条（见第六节） | 小 |
| `references/templates/agent-SKILL.md` | 取数流程加一条：带 governedRef 的指标优先 `run_metric.py` 平台直查（平台侧计算，口径权威），失败降级原三层取数路径 | 小 |
| 增量通道 I3 | 新确认的指标条目重跑对齐（只处理增量） | 小 |
| `workbench.py --check` | 体检报告可选加"指标中心引用覆盖率"（governedRef 命中条数/总条数） | 可选，P2 |

取数路径定位：`run_metric.py` 直查排在"卡片缓存 → 数据集级 → 明细层"三层**之前**——命中 governedRef 的问题走平台计算（权威口径 + 平台侧性能），粒度不够再降级。红线 14（取数必经白名单脚本）不破：metric query 一律经 run_metric.py，禁止裸调 `guancli metric query` 取数。

## 五、边界（防变重，必须守住）

本向导只做：**引用、顺手创建原子指标（≤10 条）、一次性推荐**。

以下需求**一律路由到专项 skill**（guandata-metric-migration），不在本向导展开：

- 指标体系建设、业务域划分、目录设计
- 批量迁移与归并剔除（同名多口径的系统性收敛）
- 复合/派生指标的批量梳理（依赖排序、公共维度映射）
- 业务确认工作簿与平台实施工作簿

路由话术："这部分超出搭建分析助手的范围了——您需要的是一次系统的指标梳理，有专门的迁移流程可以做（业务确认工作簿 → 平台实施工作簿 → 批量创建）。这次先把助手搭完，之后需要的话我们单开一轮做指标建设。"

## 六、新增红线（建议写入 SKILL.md 红线区）

17. **指标中心三条**：对齐只做引用/顺手创建原子指标/一次性推荐，指标体系建设路由专项 skill 不展开；`metric query` 取数必经 run_metric.py 白名单校验；指标中心口径与看板口径不一致时列入拍板组请用户裁决，禁止 AI 自行二选一。

## 七、开放问题（实施时确认）

1. **三态判定的错误形态**：guancli 对"未开通指标中心"和"无权限"的具体返回（错误码/错误文本）需实机确认；确认前统一按"不可用"降级，文案只说结论不暴露技术原因（红线 3）。
2. **guanmetric 可用性**：顺手创建依赖 guanmetric 组件已安装且已认证——preflight 是否需要加一项轻量探测，或首次使用时再提示安装，实施时定（倾向后者，保持 preflight 不膨胀）。
3. **一致性核对的深浅**：description 文本比对有歧义时宁可标"待确认"不硬判——引用错了比不引用更糟（与 v4.1"口径混乱有毒"同一逻辑）。
