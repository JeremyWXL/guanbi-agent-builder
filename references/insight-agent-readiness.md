# 洞察Agent 看板就绪度：要求、评分与调整规则

> 本文件是「洞察Agent 看板就绪诊断」通道的规则大脑。它把观远官方文档与项目实践蒸馏成可执行规则，供 AI 在诊断时引用；脚本只做机械判定，业务判断必须回到这里并请用户确认。
>
> 适用对象：观远洞察Agent（Data Agent > 洞察智能体 > 仪表板智能体）。
> 不适用：ChatBI 问数、DecideX 经营决策、仪表板洞察（单看板自动解读）、WorkBuddy data agent 搭建（走八步向导）。

## 0. 一句话判断

**给人看的看板 ≠ 给 Agent 看的看板。**

人可以手动筛选、跳转、凭经验补上下文；Agent 一次性读取页面结构，按筛选器传参、按卡片路由、按层级下钻。页面过大、口径不清、筛选器缺失、层级混在一起，都会让 Agent 跑偏。诊断的目的不是把现有看板“接给大模型”，而是判断它能不能被 Agent 稳定执行，并给出改造成 Agent 可执行结构的动作。

## 1. 产品硬约束（官方）

以下规则来自观远官方文档，违反即为阻断项（blocker），不能靠“建议优化”绕过。

### R-01 数据范围最多 10 张仪表板

- **要求**：一个洞察Agent 的「数据范围」最多选择 10 个页面。
- **判定**：`pageCount > 10` → 组合级阻断。
- **动作**：按目标业务问题做取舍，保留最贴近主链路的 ≤10 张；其余拆成第二个智能体（按主题/组织/场景），或先移出数据范围。禁止“先都放进去试试”。

### R-02 每张仪表板必须配置联动筛选器

- **要求**：数据范围中的每张仪表板都要手动选择筛选器，供 Agent 跨页联动时动态传参。
- **判定**：页面没有「在筛选栏内（`inFilterBar=true`）且有关联卡片（`linkedCardCount>0`）」的筛选器 → 页面级阻断。
- **补充**：`linkedCardCount>0` 但不在筛选栏的筛选器，可能是隐藏筛选器/时间宏，只算“候选”，需要用户在 BI 里确认能否被洞察Agent 选中；不能直接当通过。
- **动作**：至少配置一个业务公共维度筛选器（区域/门店/品类/渠道），优先选择跨页共用的字段；时间筛选器单独确认。

### R-03 环境与功能前提

- **要求**：BI 8.1 及以上；仪表板洞察可正常使用；洞察Agent License 已开通；模型能力满足深度洞察要求。
- **判定**：CLI 无法完整验证 License 与功能开关 → 在 A1 让用户确认；未确认时报告标注“环境前提待确认”，不阻塞结构诊断。
- **动作**：不满足时先走环境开通，不进入看板改造。

### R-04 业务范围必须清晰

- **要求**：「业务范围」必填，用于意图识别阶段拦截越界问题。
- **判定**：用户没有给出 1–3 个目标业务问题时，报告不出“业务覆盖”结论，只出结构诊断。
- **动作**：把业务范围写成“对象 + 场景 + 决策”的一句话，例如“连锁零售单店经营异常定位与归因”，不写“数据分析”“经营分析”这类泛词。

### R-05 指标口径由看板固化，Agent 不自创

- **要求**：指标口径、维度定义、分析框架由看板 Schema 固化；Agent 只能调用已有指标，不能自己发明口径。
- **判定**：同名指标在不同卡片/不同看板公式不一致 → P0；复合指标依赖 Agent 临时计算（如让模型自己算比率）→ P1。
- **动作**：统一到同一数据源与同一公式；能在数据集/看板层算好的，不在 Agent 层算；口径冲突逐条请业务拍板，禁止 AI 二选一。

### R-06 上下文可控

- **要求**：单页卡片数量、明细行数、跨页数量必须在 Agent 可稳定读取的范围内。
- **判定**：
  - 单页数据卡 > 20 → P0；13–20 → P1；< 5 → P1（覆盖偏窄）。
  - 明细表原始行数 > 10,000 → P0；未采样 → P2“未实测”。
- **动作**：拆分页面、把明细聚合到日/商品/门店粒度、增加中间层、限制默认时间范围。禁止把“全量明细”直接塞给 Agent。

## 2. 看板设计要求（项目方法论）

以下规则来自洞察Agent 项目落地实践，违反通常为 P0/P1，按影响排序。

### R-07 一张看板只解决一个清晰问题

- **要求**：每张看板有明确的业务问题和调用时机；不把多层级、多主题、大明细堆在同一页。
- **判定**：单页数据卡 > 20、卡片主题明显分散（命名分属多个业务域）、同一页既有集团总览又有单店明细 → P0/P1。
- **动作**：按“总览 / 定位 / 明细”或“主题”拆分；每页写一句“这张看板适合在哪一步调用”。

### R-08 指标在 BI 或数据集层算好

- **要求**：Agent 只做筛选、读取、比较、解释、归因和总结，不临时计算复杂指标。
- **判定**：卡片度量是原始字段的临时聚合、比率指标用 `AVG(明细比率)`、复合指标没有公式定义 → P1。
- **动作**：把指标沉淀为数据集计算字段或卡片度量；比率型指标统一为“分子分母分别求和再相除”。

### R-09 所有卡片有明确时间范围和筛选条件

- **要求**：卡片能说清“数据是什么期间、什么范围”；页面有时间筛选器或时间参数。
- **判定**：无时间筛选器、无时间参数、卡名锁死固定期间（且无时间筛选）→ P0/P1。
- **动作**：补时间筛选器/时间宏；卡名写清期间；默认时间范围要窄到 Agent 可稳定读取。

### R-10 卡片标题能被 Agent 理解

- **要求**：卡名不依赖业务人员心里补充；避免“图1”“副本”“未命名”“8月出杯”这类名称。
- **判定**：空名、纯编号、重复名、含“副本/测试/临时/未命名”、时间锁死 → P1/P2。
- **动作**：改成“指标 + 维度 + 口径”的可读名称，例如“各区域单店日均销售额（月累计）”；重名卡用维度/口径后缀消歧。

### R-11 下钻字段必须有筛选器承接

- **要求**：上一层传给下一层的是筛选条件和结论，不是全量数据；下钻字段必须能通过筛选器传入。
- **判定**：卡片行维度里出现区域/省/市/门店/品类/渠道等层级字段，但页面没有对应筛选器 → P1；关键公共维度完全没有筛选器 → P0。
- **动作**：补筛选器；筛选器字段名与卡片维度字段名保持一致；不要让 Agent 从全量明细里猜筛选条件。

### R-12 分层下钻：总览 → 定位 → 明细

- **要求**：第一层判断整体是否异常；第二层定位异常集中在哪些区域/渠道/品类/对象；第三层进入可行动明细。每层有筛选器承接。
- **判定**：所有看板都停留在总览层（无明细层）→ P1；只有明细没有总览 → P1；层级之间无共享维度 → P0（见 R-13）。
- **动作**：补总览页/明细页；中间层可按需增加；每层只承载该层需要解决的问题。

### R-13 跨页联动必须有共享维度

- **要求**：主从Agent 跨页传参依赖共同的筛选维度；没有共享维度，联动只能靠模型猜。
- **判定**：各页「筛选栏内联动筛选器」的字段名交集为空 → P0；交集只有时间维度 → P1（时间只能限定范围，不能定位对象）。
- **动作**：统一公共维度命名（如“区域/省份/城市/门店编码”），每页都配置同一字段的联动筛选器；字段名不一致时先在 BI 里统一。

### R-14 批量分治必须定义边界

- **要求**：单对象分析稳定但对象数量很多时，采用批量分治；必须定义批量对象、分批规则、单对象模板、批内聚合、跨批汇总、失败重试、强制遍历。
- **判定**：页面存在大量对象（SKU/门店/经销商）但没有分批/汇总设计 → P1；依赖“只输出 Top N” → P0（会漏长尾）。
- **动作**：加对象清单页 + 单对象分析页 + 汇总规则；明确“全量遍历/允许 Top N”的业务要求。

### R-15 禁止项

- 不让 Agent 从全量明细里猜筛选条件。
- 不让 Agent 临时计算复杂指标作为最终结论。
- 不把多层级、多主题、大明细堆在同一页。
- 不让多个提示词来源互相冲突（仪表板默认洞察思路 vs Agent 自定义思路）。
- 不用假数据判断业务分析逻辑是否成立。

### R-16 真实数据验证

- **要求**：用客户真实问题、历史会议问题、历史报告问题测试；先测诊断准确性，再测建议质量。
- **判定**：诊断阶段至少确认“看板数据真实、期间覆盖完整、筛选器实际生效”；无法确认时标注“待验证”。
- **动作**：把真实问题清单纳入配置衔接；改造后按同一组问题复测。

## 3. 五种组织模式与选择树

诊断的最终建议必须落到一种主模式（可带备选），不能只说“优化一下”。

| 模式 | 适用情况 | 判断信号 | 典型结构 |
|---|---|---|---|
| 一张宽表 | 数据量小、对象少、链路可一次读完 | 单页可承载、对象 < 几十、无多层组织 | 一张明细宽表 + 少量筛选器 |
| 多层下钻 | 总量大，需按组织/区域/对象逐层缩小范围 | 有集团→区域→门店/品类层级；每层数据量大 | 总览页 → 定位页 → 明细页，逐层传筛选条件 |
| 主从Agent | 需要跨看板整合结论，主Agent 规划、子Agent 聚焦 | 多张看板、分析路径不固定、需要综合报告 | 主Agent 规划步骤 → 子Agent 单页分析 → 主Agent 汇总 |
| 批量分治 | 单对象分析可靠，但对象数量太多 | SKU/门店/经销商成百上千；单对象模板稳定 | 对象清单 → 分批 → 单对象分析 → 批内聚合 → 跨批汇总 |
| 链路复盘 | 关注对象从前到后的全过程 | 商品开发→采购→销售→库存；订单→履约→售后 | 按阶段拆页，阶段间用对象 ID 串联 |

选择树：

```
对象少、单页可承载、链路一次读完 → 一张宽表
需要集团/区域/门店逐层定位 → 多层下钻
需要跨看板整合结论、主Agent 规划 → 主从Agent
单对象分析稳定、对象数量很多 → 批量分治（必须定义分批/遍历/汇总）
关注对象从开发到销售/库存的全过程 → 链路复盘
```

组合是允许的，例如“多层下钻 + 主从Agent”（总览/定位/明细三层，主Agent 跨层规划）。但主模式必须唯一，避免建议发散。

## 4. 评分模型

评分只衡量**结构可执行性**，不衡量业务价值。业务链路是否成立，由“场景链路评估”单独给出，并请用户确认。

### 4.1 页级就绪度（100）

| 维度 | 权重 | 机械证据 | 扣分规则（建议） |
|---|---:|---|---|
| 场景聚焦与可理解 | 15 | 数据卡数、卡名重复/不可读、页面说明/文本卡 | 5–12 卡满分；<5 或 13–20 扣 2；>20 扣 5；重名/不可读每类扣 2；无说明扣 2 |
| 指标可直读 | 20 | 公式冲突、比率公式安全性、参数化指标 | 无冲突满分；每个冲突扣 4；比率公式风险扣 4；参数化无承接扣 4 |
| 联动与筛选承接 | 25 | 联动筛选器、时间筛选、关键维度覆盖 | 无联动筛选器 0（阻断）；无时间筛选扣 7；关键维度覆盖按比例给分 |
| 分层与下钻 | 20 | 下钻卡/层级维度、明细层、筛选承接 | 无下钻扣 8；无明细层扣 6；下钻字段无筛选器扣 6 |
| 上下文可控 | 10 | 明细行数、卡片数、重复卡 | 行数 >1 万 0；未实测扣 3；卡片 >20 扣 3；重复卡扣 2 |
| 可运维 | 10 | 更新时间、时间锁死卡、筛选器可用性 | 停更 >90 天扣 3；时间锁死扣 3；隐藏筛选器只算候选扣 2 |

### 4.2 组合级就绪度（100）

| 维度 | 权重 | 判定 |
|---|---:|---|
| 每页联动筛选器齐备 | 25 | 有联动筛选器的页数 / 可用页数 × 25 |
| 跨页共享联动维度 | 20 | 有非时间共享维度满分；只有时间 10；无 0 |
| 跨页口径一致 | 20 | 无冲突满分；每个跨页冲突扣 5 |
| 无冗余（重叠卡片） | 15 | 重叠卡片占比 <10% 满分；10–30% 扣 5；>30% 扣 10 |
| 层级完整（总览/定位/明细） | 10 | 三层齐全 10；缺一层 5；只有一层 2 |
| 页数预算（≤10） | 10 | ≤10 满分；>10 为 0 且触发 R-01 |

### 4.3 总分与等级

```
总分 = 页级均分 × 60% + 组合级 × 40%
```

| 等级 | 分数 | 含义 |
|---|---:|---|
| 可直接配置 | ≥80 | 结构上可直接放进洞察Agent 数据范围 |
| 小改后配置 | 65–79 | 补少量筛选器/改名/去重即可 |
| 需改造 | 50–64 | 需要拆分/合并/补层/统一口径 |
| 不建议直接配置 | <50 | 先重构看板或换知识源 |

阻断收敛：

- ⛔ 不可用页（取不到/大屏/0 数据卡）不进入页级均分，单列“不可用页面”。
- 任一页存在 R-02 → 该页不进“可直接配置”，总分最高“需改造”。
- 超过 10 页且未取舍，或可用页为 0 → 总分封顶 49，等级“不建议直接配置”。
- 报告顶部单列“先解决这 N 个阻断项”，不混进普通建议。

## 5. 常见失败模式 → 诊断信号 → 调整动作

| 失败模式 | 诊断信号 | 调整动作 |
|---|---|---|
| 上下文爆掉 | 单页卡片 >20；明细行数 >1 万；多层堆一页 | 拆分页面；明细聚合；加中间层；限制默认时间范围 |
| 筛选器缺失 | 关键维度无筛选器；下钻只能从全量明细猜 | 补筛选器；统一字段名；每页至少一个联动筛选器 |
| 跨页传参失败 | 各页筛选器字段不一致；无共享维度 | 统一公共维度；每页配置同字段联动筛选器 |
| 口径冲突 | 同名指标多算法；不同页同一指标公式不一致 | 统一数据源与公式；指标中心已发布口径优先；逐条请业务裁决 |
| 单页多主题 | 卡名分属多个业务域；一页既有总览又有明细 | 按主题/层级拆分；每页写调用时机 |
| 无明细层 | 只有汇总卡，结论到不了对象 | 补明细页/对象清单；用对象 ID 串联 |
| 无总览层 | 只有明细，无法先判断哪里异常 | 补总览页；先抓关键异常再下钻 |
| 卡片不可理解 | 空名/编号/副本/时间锁死/重名 | 改名；加口径后缀；清理副本 |
| 数据停更 | 更新时间 >90 天 | 确认是否仍在维护；停更页移出数据范围 |
| 批量遍历不完整 | 只输出 Top N；无分批/汇总 | 定义分批、强制遍历、结果暂存、二次汇总 |
| 提示词冲突 | 仪表板默认洞察思路与 Agent 思路不一致 | 隔离或明确优先级；默认思路只保留一套 |
| 幻觉 | 编造分类/金额/原因 | 看板固化指标与分类；加证据要求与禁用规则 |

## 6. 整合建议的生成纪律

### 6.1 六类页面动作

| 动作 | 何时用 | 必须写清 |
|---|---|---|
| 保留 | 结构就绪、服务于目标问题 | 保留理由、建议的联动筛选器 |
| 改造 | 页面有价值但缺筛选器/命名/口径 | 改什么、改完达到什么标准 |
| 拆分 | 单页 >20 卡、多主题、多层混在一起 | 拆成几页、每页主题、层级、筛选器 |
| 合并 | 跨页同数据集+同指标+同维度重复 | 保留哪页、合并哪些卡片、删除哪些 |
| 新建 | 缺总览/定位/明细层，或缺公共维度承接 | 新页目的、层级、核心卡片、筛选器（禁止只写“新建一个看板”） |
| 移出 | 不服务目标问题、不可用、停更、超 10 页预算 | 移出理由、替代页 |

### 6.2 优先级

- **P0（阻断/准确性）**：R-01、R-02、R-05、R-06；无时间筛选；无共享联动维度；无可用页。
- **P1（覆盖/结构）**：关键维度筛选缺失；缺总览/明细层；跨页重复；13–20 卡；停更 >90 天；批量无分治。
- **P2（体验/可运维）**：卡名不可读；无页面说明；隐藏筛选器只算候选；行数未实测；重复筛选器。

### 6.3 配置衔接（诊断报告必须带）

写法细则见 `references/insight-agent-thinking-guide.md`（探索型 / 报告型两套模板）与 `references/insight-agent-card-reuse.md`（卡片级复用/重建）。

- **联动筛选器**：每页给出「筛选器名 + 字段 + cdId」，只选 `inFilterBar=true` 且 `linkedCardCount>0` 的；优先跨页共用字段。
- **卡片复用（cardReuse）**：有拆分/合并/新建页时必填。只挑符合洞察Agent 要求、用户看惯的卡片在新工程用 `createCard()` 重建（`method=rebuild`），或留在原页跨页使用（`method=keep`）；**不整页另存**，避免把冗余卡片/数据带过去。先用 `extract_card_skeletons.py` 抽骨架，再 `guanvis init`/`preview`/`publish`。
- **业务范围**：一句话，写“对象 + 场景 + 决策”，不写泛词。
- **Agent 类型**：先判断探索型 / 报告型 / 混合型。探索型偏发散提问、动态规划；报告型偏固定场景、固定交付。
- **默认分析思路**：
  - 探索型写“路径原则”：看板路由表、下钻/回退规则、终止条件、弹性边界；**不写死唯一流程**。
  - 报告型写“步骤序列”：Step 1…N，每步绑定看板/核心问题/筛选参数/输出/进入条件/终止条件。
- **步骤计划（stepPlan）**：每步至少写清 goal、dashboards、coreQuestions、filters、output、nextIf、stopIf；下一步只带结论 + 筛选条件 + 待验证假设，不带全量明细。
- **报告框架 / 用户提问示例**：报告型必须给章节框架和 ≥3 个“对象+期间+问题+决策”的提问示例。
- **输出要求**：必须带数据范围与口径、关键结论要有证据、建议要绑定具体对象。
- **业务知识缺口**：看板推不出的指标定义、异常阈值、责任部门映射、业务禁忌，列成待确认清单。
- **分析专家**：只有跨多个业务域、分析路径差异大或交付物不同才拆；单域不要为了“看起来完整”硬拆。

### 6.4 证据纪律

- 每条发现必须有证据：卡片名/cdId、筛选器名/字段、行数、公式原文、页面 mtime。
- 区分三类结论：**机械判定**（脚本可复算）、**推断**（层级/主题判断，需用户确认）、**待确认**（业务链路/阈值/责任）。
- 禁止无证据的“建议优化”“建议合并”“建议拆分”。
- 禁止把“诊断”说成“已改造完成”；改造动作是建议，不是执行结果。

---

## 7. 报告口径与话术

- 对业务用户说“看板/卡片/分析助手/洞察Agent”，不说 JSON、Schema、API、cdId（除非用户是实施人员且主动问）。
- 报告开头先给结论：能不能直接配、先改哪三件事；不要先铺一堆指标。
- 阻断项单独置顶，用“不解决会怎样”解释，而不是只列规则编号。
- 业务价值不夸大：结构就绪不等于洞察质量高；业务链路、口径、真实数据测试仍要单独做。
- 改造建议给“动作 + 验收标准”，例如“补区域筛选器，验收标准：在 BI 里选中华东后，页面所有卡片同步过滤，且洞察Agent 能选中该筛选器”。
