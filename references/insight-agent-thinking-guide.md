# 洞察Agent 分析思路写作指引（探索型 / 报告型）

> 适用对象：观远洞察Agent（Data Agent > 洞察智能体 > 仪表板智能体）的「分析思路」配置。
> 不适用：WorkBuddy data agent 的 `insightThinking.md`（那是本工具八步向导产出的助手框架，不是洞察Agent 后台配置）。
>
> 本指引解决一件事：**怎么把业务专家的分析脑回路，写成 Agent 能稳定执行的“选看板 → 问问题 → 带结论 → 进下一步”的规则。**

---

## 0. 一句话原则

分析思路不是把流程写死，而是教 Agent 每一步回答四个问题：

1. **为什么看**：这一步要解决用户的哪个分析目标？
2. **看哪张看板**：哪张看板最适合回答这个问题？为什么不是别的看板？
3. **看什么**：这张看板上核心看哪些卡片、指标、维度？必须带什么筛选参数？
4. **带走什么**：这一步得出什么结论、什么证据、什么筛选条件，交给下一步？

核心循环：

```
用户目标
  → 选择看板
  → 明确本步核心问题
  → 选择筛选参数
  → 读取 / 比较 / 归因
  → 形成结论（带数据范围与证据）
  → 带着结论和筛选条件进入下一步（或终止）
```

**关键纪律**：下一步接收的是“结论 + 筛选条件”，不是上一步的全量明细。把全量数据往下传，上下文一定会爆，分析也会跑偏。

---

## 1. 先判断 Agent 类型：探索型 / 报告型 / 混合型

同样是“分析思路”，两种 Agent 的写法完全不同。先判断，再动笔。

| 判断项 | 探索型分析 Agent | 报告型 Agent |
|---|---|---|
| 用户问题 | 发散、开放、临时、多轮追问 | 场景明确、问题可枚举、周期性重复 |
| 分析路径 | 不固定，需要动态规划 | 相对固定，可以写成步骤序列 |
| 交付物 | 结论 + 下一步建议，形式不固定 | 固定报告/播报/会议材料 |
| 用户角色 | 管理者、分析师，边看边问 | 经营例会、周报/月报、专项复盘 |
| 提示词弹性 | **高**：给原则、路由、边界，不写死步骤 | **低**：给明确步骤、进入/退出条件、报告框架 |
| 步骤写法 | 路径原则 + 看板路由表 + 终止条件 | Step 1…N，每步绑定看板/卡片/筛选/输出 |
| 交付框架 | 可选，轻量 | 必须给章节结构和示例 |
| 用户提问示例 | 可选，用于引导但不限制 | 必须给 3–5 个，引导用户把问题问清楚 |

**混合型**：默认走探索型，另配一个或几个“报告型分析专家”。用户自由提问时走默认思路；明确说“出月报/开经营会”时命中报告型专家。不要把所有场景都塞进一个固定流程。

判断问句（直接问用户）：

> “这个洞察Agent 主要是给管理者自由提问、边问边下钻（探索型），还是固定场景出报告/播报（报告型）？如果两者都有，我们可以默认探索型，再配一个报告型专家。”

## 2. 两种类型都必须写的六块内容

### 2.1 角色与业务范围

一句话说清：**是谁、看什么业务、回答到什么边界**。

- 好例子：“连锁零售单店经营诊断助手，围绕人、品、店、客、销五个维度，回答单店/区域/品类的经营异常与归因；不回答战略、组织、外部市场判断。”
- 差例子：“数据分析助手，什么都能问。”

业务范围会用于意图识别阶段拦截越界问题，所以边界要写清楚，不要写成万能助手。

### 2.2 看板地图（Dashboard Map）

不要只列看板名，要写清每张看板的“岗位”：

| 看板 | 解决什么问题 | 适合哪一步 | 必须带的筛选参数 | 不该用来做什么 |
|---|---|---|---|---|
| 集团经营总览 | 判断整体是否异常、哪些指标在动 | 第 1 步总览定位 | 时间范围 | 不要在这里追单店原因 |
| 区域/片区分析 | 定位异常集中在哪些区域 | 第 2 步维度拆解 | 时间、区域 | 不要用它给单店建议 |
| 单店明细 | 追到具体门店和可行动对象 | 第 3 步对象下钻 | 时间、区域、门店编码 | 不要用它做集团汇总 |
| 商品/品类分析 | 看品类结构、单品表现 | 第 2/3 步 | 时间、品类、商品 | 不要用它代替门店诊断 |

写法要求：

- 每张看板只写一个“主岗位”；一张看板可以出现在多个步骤，但每次的意图要不同。
- 写清“不该用来做什么”，防止 Agent 拿汇总页答明细问题。
- 筛选参数写业务字段名（区域/门店编码/品类），不要写内部 ID。

### 2.3 单步分析契约（Step Contract）

每一步都必须能回答下面 8 个问题。探索型可以不写死步骤序号，但每个“路径节点”仍要有这份契约。

```
Step N：
  目的：这一步要解决用户的哪个问题？
  选哪张看板：看板名 + 为什么选它（不选别的）
  核心问题：本步最多 2–3 个问题，按优先级排
  看什么：核心卡片 / 指标 / 维度
  筛选参数：必须带哪些筛选条件？参数从哪来？
  本步输出：结论 + 数据范围 + 证据（卡片/口径/期间）
  进入下一步的条件：满足什么条件继续？带什么结论和参数？
  终止条件：什么情况下停止，不再下钻？
```

**最容易被省略、但最关键的是“进入下一步的条件”和“终止条件”**。没有这两个，Agent 会无限下钻或提前收尾。

### 2.4 上下文传递规则

每一步只传三类东西：

1. **结论**：例如“华东区域单店日均同比下降 8%，主要来自江苏”。
2. **筛选条件**：例如“区域=华东；时间=2026-09；品类=饮品”。
3. **待验证假设**：例如“怀疑是加盟商结构变化，下一步看加盟商维度”。

不要传：

- 上一步的全量明细；
- 与当前问题无关的卡片内容；
- 没有数据范围的“感觉”。

### 2.5 证据与口径纪律

- 每个结论必须能回到：看板 → 卡片 → 指标口径 → 数据期间。
- 指标口径以看板/指标中心为准，Agent 不自创口径。
- 数据不足时写“待验证”，不要编原因、编分类、编金额。
- 跨页比较前，先确认同名指标口径一致；不一致要显式声明差异。

### 2.6 输出与禁止项

输出要求至少写清：

- 结论先行还是数据先行；
- 是否必须带数据范围、口径、证据；
- 建议是否必须绑定具体对象；
- 报告型是否按固定章节输出；
- 语言风格（经营例会口语 / 正式报告 / 群播报）。

禁止项至少写：

- 禁止编造业务分类、金额、原因；
- 禁止跨口径比较；
- 禁止未取数就下结论；
- 禁止超出业务范围回答；
- 禁止把“待验证”写成确定结论。

## 3. 探索型分析 Agent 怎么写

### 3.1 核心策略：写“路径原则”，不写死步骤

探索型的用户问题不可枚举，写死 Step 1/2/3 会让 Agent 只会走一条路。正确写法是：

- **给起点**：先看哪张总览看板、先判断什么。
- **给路由**：遇到哪类问题，优先选哪张看板、看哪些卡片。
- **给下钻规则**：什么条件下继续、往哪个维度钻、什么时候停。
- **给弹性边界**：哪些必须遵守，哪些可以自由组合。

### 3.2 推荐结构

```
# 角色与业务范围
# 看板地图
# 分析起点
# 路径选择原则（问题类型 → 候选看板 → 核心问题）
# 下钻与回退规则
# 筛选参数传递规则
# 终止条件
# 证据与输出要求
# 禁止项
```

### 3.3 路径选择原则怎么写

用“问题类型 → 候选看板 → 核心问题 → 下一步”的表，而不是步骤序号：

| 用户问题类型 | 优先看板 | 本步核心问题 | 典型下一步 |
|---|---|---|---|
| 整体怎么样 / 有没有异常 | 集团经营总览 | 哪些核心指标偏离？偏离多大？ | 异常指标 → 区域/品类定位 |
| 为什么下降 / 原因是什么 | 区域或品类分析 | 哪个区域/品类贡献最大？ | 追到门店/单品 |
| 哪些对象需要处理 | 单店/单品明细 | 异常对象清单、影响排序 | 单对象诊断 |
| 某个对象怎么回事 | 单对象明细 | 该对象的指标、结构、异常点 | 归因/建议 |
| 下一步怎么办 | 前序结论 + 规则 | 责任映射、优先级、动作 | 输出建议/报告 |

写法要求：

- 每类问题给 1–3 张候选看板，不要给全部看板。
- 每张看板写 2–3 个核心问题，不要写“分析所有指标”。
- 明确“如果数据不支持，就回到上一级或换看板”，允许回退。

### 3.4 下钻与终止规则

**继续下钻的触发条件**（满足任一）：

- 单一对象贡献超过总变化的 30%；
- 某区域/品类/渠道贡献主要缺口；
- 异常集中在少数对象；
- 用户明确问“为什么/是谁/怎么办”。

**停止下钻的条件**（同时满足）：

- 找到主异常源；
- 影响已量化；
- 已定位到可执行对象；
- 能给出有依据的建议，或明确说明还缺什么数据。

**步数上限**：建议 3–6 步；超过时先给阶段性结论，不要无限追。

### 3.5 弹性边界

必须遵守（硬规则）：

- 只使用数据范围内的看板与卡片；
- 指标口径以看板为准；
- 筛选参数必须来自看板已声明的筛选器；
- 结论必须有数据范围和证据；
- 不编造、不超范围、不跨口径比较；
- 达到终止条件就停。

可以自由（软空间）：

- 步骤顺序（只要逻辑递进）；
- 同一看板多次使用（意图不同）；
- 维度选择与下钻深度；
- 是否先给阶段性结论；
- 建议的呈现形式。

### 3.6 探索型示例片段

```
你是连锁零售单店经营诊断助手。用户可能从任何经营问题切入，你不要机械执行固定步骤，
而是按下面的原则动态选择看板和路径：

1. 先判断问题类型：整体异常 / 原因追问 / 对象诊断 / 行动建议。
2. 整体异常先看《集团经营总览》，确认偏离最大的 1–2 个核心指标；
   不要在这一步解释原因。
3. 原因追问按指标选择《区域分析》或《品类分析》，先找贡献最大的区域/品类；
   如果贡献分散，回到总览确认是否口径/期间问题。
4. 需要落到对象时再看《单店明细》，用区域/门店编码筛选；
   不要用总览页代替单店结论。
5. 每一步只带走：结论 + 数据范围 + 筛选条件 + 待验证假设；
   不要把明细表传给下一步。
6. 满足以下条件就停止：找到主异常源、量化影响、定位到可执行对象、能给出建议。
7. 如果数据不足，明确说“还缺什么”，不要编原因。
```

## 4. 报告型 Agent 怎么写

### 4.1 核心策略：写清步骤、交付框架、提问示例

报告型的用户问题相对固定，目标是把“每次都要人工做的报告”变成稳定流程。写法要更确定：

- **固定步骤序列**：Step 1…N，每步绑定看板/卡片/筛选/输出；
- **交付成果框架**：报告章节、每章要回答什么、证据要求；
- **用户提问示例**：3–5 个，引导用户把场景、对象、期间、口径说清楚；
- **终止与缺数处理**：哪一步没数据时怎么降级。

### 4.2 推荐结构

```
# 角色与业务范围
# 适用场景（什么情况下用这个报告型 Agent）
# 固定分析步骤（Step 1…N，每步含看板/核心问题/筛选/输出/进入条件）
# 报告交付框架（章节结构）
# 用户提问示例
# 缺数与异常处理
# 证据与输出要求
# 禁止项
```

### 4.3 固定步骤模板

```
Step 1 总览定位
  看板：《集团经营总览》
  核心问题：本期核心指标是否偏离？偏离最大的 1–2 个指标是什么？
  筛选：时间=本期；对比=上期/同期
  输出：一句话定调 + 核心指标表（实际/目标/同比/状态）
  进入下一步：存在明显偏离 → Step 2；否则输出“本期无显著异常”并结束

Step 2 维度拆解
  看板：《区域分析》/《品类分析》
  核心问题：偏离主要集中在哪些区域/品类？贡献额和贡献率是多少？
  筛选：时间=本期；区域/品类=全部
  输出：Top 异常维度 + 贡献排序
  进入下一步：单一对象贡献 >30% → Step 3；否则 Step 4

Step 3 对象下钻
  看板：《单店明细》/《单品明细》
  核心问题：具体哪些门店/单品？异常表现是什么？
  筛选：时间=本期；区域=Step 2 锁定；门店编码=异常清单
  输出：异常对象清单 + 单对象证据
  进入下一步：需要归因 → Step 4

Step 4 归因与建议
  看板：前序结论 + 业务知识（阈值/责任映射）
  核心问题：主因是什么？责任部门是谁？优先做什么？
  输出：根因 + 责任映射 + P0/P1/P2 建议
```

### 4.4 报告交付框架

给出章节骨架，不要只写“生成报告”：

```
1. 结论摘要：一句话定调 + 3 条关键发现
2. 核心指标：实际/目标/同比/环比/状态
3. 异常与机会清单：对象、表现、影响、优先级
4. 根因分析：主因/次因、贡献额、证据
5. 责任映射：问题 → 部门/角色
6. 行动建议：P0（立即）/P1（本月）/P2（结构性）
7. 附录：数据范围、口径、待验证问题
```

每个章节写清：

- 必须回答的问题；
- 必须带的证据；
- 没有数据时怎么写（“待验证/数据缺口”）。

### 4.5 用户提问示例

报告型必须给 3–5 个示例，引导用户把问题问清楚。示例要包含：**对象 + 期间 + 指标/问题 + 期望决策**。

好例子：

- “出一份 2026 年 9 月华东区域单店经营诊断报告，重点看单店日均、客单价和品类结构。”
- “对比 9 月和 8 月，找出华东下滑最严重的 20 家门店，给出原因和责任部门建议。”
- “本周经营例会：按人、品、店、客、销五个维度，输出需要重点讨论的 5 个问题。”

差例子：

- “分析一下经营情况。”（没有对象、期间、决策）
- “为什么下降了？”（没有指标、范围）

### 4.6 缺数与异常处理

- 某一步数据缺失：写明“哪张看板/哪个指标缺”，不要用其他口径替代。
- 数据量过大：先聚合到日/商品/门店粒度，再分析；不要拉全量明细。
- 口径冲突：先声明冲突，请业务确认；不要自行二选一。
- 结论不确定：写“待验证假设”，并说明需要补什么数据。

## 5. 看板路由表怎么画

路由表是分析思路的“地图”，建议单独成节：

| 用户意图 | 候选看板（≤3） | 核心卡片/指标 | 必带筛选 | 本步输出 | 下一步 |
|---|---|---|---|---|---|
| 整体有没有异常 | 集团经营总览 | 核心 KPI、趋势 | 时间 | 偏离指标 + 幅度 | 维度拆解 |
| 为什么下降 | 区域/品类分析 | 区域/品类贡献 | 时间、区域/品类 | Top 贡献对象 | 对象下钻 |
| 哪些对象要处理 | 单店/单品明细 | 对象指标、异常标记 | 时间、区域、对象 ID | 异常清单 + 排序 | 单对象诊断 |
| 某个对象怎么回事 | 单对象明细 | 指标结构、趋势、对比 | 时间、对象 ID | 单对象结论 | 归因/建议 |
| 下一步怎么办 | 前序结论 + 规则 | 责任映射、优先级 | — | 建议清单 | 输出/报告 |

写法要求：

- 一行一个意图，不要把所有问题塞进一行；
- 候选看板不超过 3 张，写清“为什么选它”；
- 筛选字段用业务名称，不用内部 ID；
- 下一步写“进入什么类型的分析”，不写死具体看板名（探索型）。

## 6. 分析专家 vs 默认思路

| 配置 | 写什么 | 什么时候用 |
|---|---|---|
| 默认思路 | 通用分析骨架、探索型路径原则、证据与输出边界 | 用户问题没有命中特定专家时 |
| 分析专家 | 领域专属的用户提示词、洞察思路、输出要求、报告模式 | 问题命中专家业务范围时自动调用 |
| 业务知识 | 术语、指标口径、异常阈值、责任映射、业务禁忌 | 所有分析都需要 |

拆分专家的原则：

- **跨业务域**（门店经营 / 商品 / 渠道 / 会员）且分析路径差异大 → 拆；
- **交付物不同**（诊断报告 / 周报播报 / 专项复盘）→ 拆；
- **单域、路径一致** → 不拆，避免专家之间口径冲突。

冲突处理：

- 分析专家优先于默认思路；
- 仪表板自带洞察思路与 Agent 自定义思路要隔离，明确优先级；
- 同一指标在专家/默认思路里口径必须一致。

## 7. 与官方字段的映射

| 官方字段 | 写什么 | 主要来源 |
|---|---|---|
| 业务范围 | 角色 + 业务 + 边界，一句话 | 用户目标 / 场景 |
| 默认思路 | 通用分析骨架；探索型写路径原则，报告型写步骤序列 | 本指引第 3/4 节 |
| 输出要求 | 结论格式、证据要求、语言风格、必备要素 | 本指引第 2.6 节 |
| 分析专家 | 领域专属步骤、报告模式、输出要求 | 本指引第 6 节 |
| 业务知识 | 术语、口径、阈值、责任映射、禁忌 | 看板 + 业务访谈 |

## 8. 上线前检查清单

- [ ] 已判断 Agent 类型（探索型 / 报告型 / 混合型），并写入配置。
- [ ] 业务范围一句话说清“是谁、看什么、不回答什么”。
- [ ] 看板地图每张看板有“主岗位”和“不该用来做什么”。
- [ ] 每个步骤/路径节点有：目的、看板、核心问题、筛选参数、输出、进入条件、终止条件。
- [ ] 明确“下一步只带结论 + 筛选条件 + 待验证假设”，不带全量明细。
- [ ] 探索型有路径选择原则、下钻/回退规则、步数上限；没有写死唯一流程。
- [ ] 报告型有固定步骤、报告章节框架、≥3 个用户提问示例。
- [ ] 指标口径以看板/指标中心为准，跨页比较前先确认一致。
- [ ] 有缺数、口径冲突、超范围的处理方式。
- [ ] 有禁止项：不编造、不跨口径、不未取数下结论、不超范围。
- [ ] 分析专家与默认思路的边界清楚，不互相冲突。
- [ ] 用真实问题跑过至少 3 轮，确认路径合理、结论可追溯。

## 9. 常见反例

| 反例 | 问题 | 正确做法 |
|---|---|---|
| “先看总览，再下钻，最后给建议” | 没有看板、卡片、筛选、条件，Agent 无法执行 | 按 Step Contract 写清每步 |
| 把全量明细传给下一步 | 上下文爆炸、分析跑偏 | 只传结论 + 筛选条件 + 假设 |
| 探索型写死 Step 1–5 | 用户灵活提问时走不通 | 写路径原则 + 路由表 + 终止条件 |
| 报告型只写“生成报告” | 输出不稳定、章节缺失 | 给报告框架和每章要求 |
| 报告型没有提问示例 | 用户问得太泛，Agent 反复澄清 | 给 3–5 个“对象+期间+问题+决策”示例 |
| 默认思路与分析专家口径冲突 | 同一问题两个答案 | 明确专家优先，统一口径 |
| 只写“分析所有指标” | 没有重点、上下文超限 | 每步 2–3 个核心问题 |
| 没有终止条件 | 无限下钻 | 定义停止条件和步数上限 |

## 10. 与诊断报告的关系

本 Skill 的「洞察Agent 看板就绪诊断」在 A3 阶段会生成 `configHandoff` 草稿，其中：

- `agentType`：探索型 / 报告型 / 混合型；
- `defaultThinking`：可直接粘贴到「默认思路」的文本；
- `stepPlan`：结构化步骤（看板/核心问题/筛选/输出/条件）；
- `exploratoryRules`：探索型路径原则；
- `reportFramework`：报告型交付框架；
- `questionExamples`：报告型用户提问示例；
- `outputRequirements` / `businessKnowledgeGaps` / `expertRoles`：其余配置衔接。

报告只是草稿，最终配置仍在 BI 管理端的洞察Agent 编辑页完成。配置后用真实问题跑 3 轮以上，再逐步放开探索型弹性。
