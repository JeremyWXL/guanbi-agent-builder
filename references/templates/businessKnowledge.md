# 业务知识模板（businessKnowledge）

# 业务口径规则（经业务用户逐条确认，共 {N} 条）

{快速模式成稿时，标题行替换为：# 业务口径规则（快速模式成稿：共识口径按看板算法默认采纳，未经逐条确认，可随时逐条深化，共 {N} 条）；深化完成后改为"已逐条确认"}

1. {指标口径类：如"预算数=3.5预算数，预算达成=3.5预算达成"}
2. {指标方向类：如"费用的预算达成越低越好，收入的预算达成越高越好"}
3. {编码规则类：如"销售费用=Fin23***到Fin28***科目编码"}
4. {计算公式类：如"达成缺口=实际数-预算数"、"结构性影响=…"；第 2 步 formulas.json 的口径候选逐条确认后转写于此}
5. {口径冲突裁决类：如"退款率=退款金额/收入（渠道情况卡专用）；退款率=退款金额/GMV（趋势卡专用）"——同名指标多口径时必须标注适用范围}
5. {业务背景类：如"5月6月是618大促月"、"数据范围=国内渠道，不含光合星球事业部"}
6. {分析边界类：如"渠道合计的结构性影响是0，不单独分析，仅分析单个渠道"}
7. {SQL 口径类：若启用 SQL 直查，记录"SQL 计算口径 = XX，与看板口径 XX 的差异为 XX"、"禁止引用的冗余字段 = XX, YY, ZZ"}

---
编写要求：
- 每条规则必须来自用户确认或看板明确信息，禁止 AI 臆测
- 规则用"字段名/业务术语 = 含义/算法"的格式，确保 LLM 可直接引用
- 用户纠正过的规则在末尾保留修正记录（如"原理解 X → 用户纠正为 Y"）
- **SQL 口径类规则**：当发现 SQL 算的指标与看板口径不一致时，必须把"SQL 口径"作为一条单独的规则写入，标注差异；同时标记底层数据集中"看板卡片未使用的冗余字段"为"禁止引用"，防止后续 SQL 取数时口径混淆
