# 看板知识迁移的设计推演（2026-09-26）

> 本文件记录 v4.1–v4.3 三个迭代版本的**思考过程与决策依据**，回答"为什么这么迭代"。
> 结论条目已落入 [ROADMAP.md](../ROADMAP.md)（v4.1 看板质量前置闸 / v4.2 卡片取数加速层 / v4.3 看板角色迁移 + 设计原则第 7 条），本文是它们背后的推演原文。
> 讨论前提：BI 看板凝聚隐性业务知识，搭建 agent 的过程就是业务知识的挖掘与显性化，让通用 agent（WorkBuddy 类）在此基础上做更灵活的业务分析。

## 一、问题：看板质量不好时，能搭出多好的 agent？

### 1.1 看板承载的隐性知识分层

| 层 | 内容 | 数据集里有没有 |
|---|---|---|
| 指标口径 | 什么算"销售额"（公式、筛选、时间粒度） | 残迹：字段命名、稀疏注释 |
| 维度组织 | 按区域还是按客户层级切 | 残迹：枚举值、列画像 |
| 分析路径 | 先看总量→再看结构→下钻异常 | **几乎没有** |
| 问题空间 | 哪些组合是业务上"有意义的问法" | **完全没有** |

看板质量差时，挖掘产出系统性缺"分析路径"和"问题空间"两层。**这不是换更强的模型能补的，是信息本身不在输入里。**

### 1.2 "质量差"必须细分

- **口径混乱**（同名指标多种算法）：有毒。会把错误口径显性化进 agent，比没有知识更糟——要先"反学习"错误产物才能修。
- **覆盖不足**（只覆盖少量场景）：无害但压上限，只需标注能力边界。

### 1.3 结论

质量差的看板不是"差一点的知识源"，而是**信噪比为负的知识源**。直接挖粗糙看板，产出的 agent 带错误口径和虚假分析路径，比从数据集冷启动更难修。

由此得到两条迭代决策：

1. **口径治理是挖掘流水线的前置工序，不是可选项**（→ v4.1：看板 agent-ready 评分，低分先治理再挖掘）。
2. **数据集冷启动路径可以保留，但必须诚实标注**：产出是"数据探索型 agent"——能答"数据里有什么"，答不了"业务上该看什么"。两层之间缺的知识必须有其他注入渠道（业务访谈、文档），不能假装它不存在。

**遗留分歧**（设计 v4.1 时无需解决，但要知道它存在）：缺失的知识能否靠查询日志/业务文档/访谈低成本补回？乐观派认为可以，悲观派认为那等于重做一次 BI 需求调研。本项目立场：补回渠道可以做，但成本不可假设为零。

## 二、问题：知识抽象出来之后，看板还剩什么价值？

（讨论范围：排除业务用户使用习惯、数据可信性验证等外部因素。）

### 2.1 容易犯的错误

把看板只看成"知识的存储"。若如此，知识进了 agent 之后看板确实被掏空。但看板至少还剩两个角色：

### 2.2 角色一：知识保鲜的锚点（grounding 作用点）

业务在变，口径会漂移。agent 里的知识层需要一个**仍在运行、仍被消费的参照物**来检测漂移。抽象出来的知识如果没有对照物，会变成无源之水——你不知道它什么时候过时了。

**看板在这里不是消费终端，是回归测试集。**

### 2.3 角色二：产出物的形态模板

agent 做灵活分析，但最终交付给业务看的常常是"一个图表 + 一个结论"。看板里沉淀的图表选型、布局、联动结构，是 agent 生成产出时最好的**渲染模板库**。挖出来的不只是"问什么"，还有"怎么呈现"。

### 2.4 结论

看板的角色是**迁移，不是消失**：从消费终端降级为 agent 的训练语料 + 漂移检测基准 + 呈现模板库。真正失去价值的只是"看板作为人与数据之间唯一界面"这一定位。

由此得到的工程决策（→ v4.3）：

1. 结构指纹（v3.1.0 已有）从"结构变了没有"扩展到"口径漂了没有"：agent 回答与看板读数定期对账，漂移即告警进纠错闭环。
2. 挖掘时必须保留**结构性元数据**（图表类型/布局/联动），只抽语义等于扔掉一半知识。
3. 从卡片联动/下钻配置抽取多轮分析路径，补 examples.json 只有单轮问答对的缺口。

## 三、问题：卡片对 agent 的取数和分析性能有帮助吗？

### 3.1 取数侧：帮助是实打实的，来自三样东西

1. **ETL 加工成果复用**：卡片背后的数据集已做完 join、清洗、口径换算、脱敏。agent 从明细取数要重做这些，且可能重做错。
2. **引擎层缓存与计算优化**：抽取数据集（Guan-Index）在内存引擎里，卡片聚合查询被 BI 引擎优化缓存。agent 走卡片/数据集 API 吃得到热数据；自己写 SQL 打底库全都没有。高频形态已知的问题，读卡片结果成本近零。
3. **权限免费继承**：数据集挂了行列权限，走卡片层取数天然继承，不用在 agent 侧重建权限逻辑（自建权限过滤的出错成本远高于省下的查询灵活性）。

### 3.2 分析侧：帮助有条件，核心约束是粒度陷阱

卡片数据集是**为这张图裁剪过的**——固定维度组合、聚合粒度，常带筛选条件（"只看华东"）。由此产生不对称：

- 问题落在卡片粒度之内：卡片既是语义模板又是物化视图，帮助极大，可零计算直接引用。
- 问题需要粒度以下下钻或跨卡片 join：卡片数据集是**负资产**——误用带筛选数据集回答全局问题，会产出隐蔽的口径错误。

关键工程决策：**区分数据集级（未筛选，可开放二次计算）与卡片级（带筛选，只作应答缓存、禁止继续加工）**（→ v4.2 P0）。

### 3.3 帮助程度：分层估计

| 查询层 | 占比（经验估计） | 卡片的帮助 |
|---|---|---|
| 高频已知问题（卡片形态直接覆盖） | 大头，日常查询主体 | 极大：直接读结果/命中缓存，成本近零 |
| 已知数据集上的新切片（粒度内重组） | 中等 | 中到高：数据集上再算，省 ETL 与权限重建 |
| 探索性 / 跨域 / 粒度以下 | 小头但往往是高价值问题 | 零到负：回明细层，还要防误用卡片 |

### 3.4 结论

把卡片定位为**物化视图 + 权限边界 + 应答缓存**，而不是分析逻辑本身。它能吃掉 agent 日常查询负载的大部分取数成本（估"取数工作量减半以上、高频问题接近即时"量级），但对 agent 的**能力上限无贡献**——上限仍由明细层和知识层决定。

放大/缩小这层收益的变量是**卡片与数据集的复用率**：多卡共用一个数据集，收益放大；一卡一数据集的专用宽表，收益只剩缓存和权限。因此数据集复用率 + 粒度覆盖应成为评估客户环境"agent-ready 程度"的指标（与 v4.1 评分模型共用）。

## 四、收束：一条迭代主线

三个问题指向同一条主线：

**看板 → agent 的迁移不是一次性的知识搬运，而是把看板降级为 agent 的持续参照物。**

- 质量门槛决定能不能挖（问题一 → v4.1 前置闸）
- 卡片分层决定取数效率（问题三 → v4.2 加速层）
- 角色迁移决定挖完之后留什么（问题二 → v4.3 漂移检测 + 模板库）

落地为设计原则第 7 条：看板是 agent 的持续参照物，不是一次性语料——挖掘前先过质量闸，挖掘后降级为漂移检测基准 + 呈现模板库，挖掘时语义与结构性元数据都要留。
