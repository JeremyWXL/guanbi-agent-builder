# 认知补充（cognitive-foundation）

> 本文件是 guanbi-agent-builder v2.0 的参考文档。核心理念：**认知补充是可选的，不是必经的；客户才是业务专家，AI 只是提供选项**。

---

## 一、设计原则

### 1.1 顺序：先看板，后补充

正确流程：
```
第 1 步：选定数据范围（选定看板）
第 2 步：看板资产学习（建立基础认知）
第 3 步：业务认知补充（可选，判断是否需要）
第 4 步：业务口径确认
...
```

**为什么这个顺序？**
- 观远原生 agent 也是先有看板，业务调研只是补充输入，不是前置条件
- 先看板能让 AI 对客户场景有初步理解，再判断"缺什么"比"盲补"更精准
- 客户是业务专家，AI 不应该替客户决定"这个行业该怎么分析"

### 1.2 可选性：客户判断是否需要

第 3 步的核心是**询问客户**，而不是 AI 自作主张：
- 客户说"不需要"→ 直接跳过，进入口径确认
- 客户说"需要"→ 提供选项，让客户选择补充方式

### 1.3 确认制：学到的东西必须客户确认

无论客户选择哪种补充方式，AI 学到的东西必须：
1. 生成可编辑的过程文件（md 格式）
2. 向客户详细展示
3. 客户确认微调后，才放行进入下一步

这是"以客户业务为准"的核心保障——防止 AI 闭门造车，把错误认知固化进 agent。

## 二、认知补充的三个选项

### 选项 A：外网行业学习（WebSearch）

**适用场景**：客户想参考行业通用分析框架，或 AI 对行业理解不够时

**操作步骤**：
1. 从看板内容提取行业关键词（如"连锁零售""财务分析""电商运营"）
2. WebSearch 学习该行业的通用经营分析框架：
   - 这个行业靠什么指标衡量健康度？
   - 这个行业的经典归因模型是什么？
   - 这个行业有哪些"行话"和隐性业务规则？
3. 生成 `industry-notes.md`（行业指标树 + 归因公式候选 + 行业术语表）
4. 向客户展示："我学习了 XX 行业的通用分析方法，总结出这几个关键点：…这些符合您的业务实际吗？需要调整吗？"
5. 客户确认后，进入第 4 步

**红线**：
- 行业知识是"参考框架"，不是"业务事实"
- 最终口径仍以客户确认为准
- 外网信息仅作启发，禁止直接当结论写进 businessKnowledge

### 选项 B：历史报告提炼

**适用场景**：客户有现成的经营分析报告/月度汇报/PPT/Excel

**操作步骤**：
1. 问客户："您手上有没有现成的经营分析报告？哪怕是一两份过期的也行"
2. 若客户提供，读取报告并提炼三类资产：
   - **汇报骨架**：报告分几章？先讲什么后讲什么？
   - **指标体系**：报告里反复出现哪些指标？用什么口径？
   - **归因套路**：报告里是怎么解释"为什么没达标"的？
3. 生成 `report-insights.md`（汇报骨架 + 指标体系 + 归因套路）
4. 向客户展示："我从报告里看到了这样的分析思路：…这是您想要的吗？"
5. 客户确认后，进入第 4 步

**红线**：
- 历史报告是最高优先级的业务输入
- 若报告与看板数据冲突，以看板数据为准（报告可能是旧口径）
- 客户没报告不是搭建的阻碍，只是少了一条捷径

### 选项 C：历史对话沉淀

**适用场景**：客户在 WorkBuddy 里有相关历史对话，且愿意授权 AI 提炼

**操作步骤**：
1. 问客户："如果您在 WorkBuddy 里有相关历史对话，我可以从中提炼您的决策习惯和关注点，需要吗？"
2. 若客户授权，用 conversation_search 检索相关历史对话
3. 提炼三类资产：
   - **决策习惯**：客户平时关注什么指标？按什么优先级？
   - **关注点**：客户最常追问什么？最关心哪些维度？
   - **常用口径**：客户习惯用什么口径？有什么特殊约定？
4. 生成 `conversation-insights.md`（决策习惯 + 关注点 + 常用口径）
5. 向客户展示："我从历史对话里看到了您的这些关注点：…这些准确吗？"
6. 客户确认后，进入第 4 步

**红线**：
- 必须客户明确授权才能检索历史对话
- 历史对话仅作参考，最终口径仍以客户确认为准

### 选项 D：暂不需要

**适用场景**：客户认为当前理解已足够，或想快速进入下一步

**操作**：直接进入第 4 步，不生成任何补充文件

## 三、诊断链模板（注入 insightThinking）

这是从观远原生 agent 逆向工程出的方法论核心。在生成 insightThinking 时，把这套"动态下钻纪律"写进去：

### 3.1 五条铁律
1. **先抓关键异常**：不平均分析所有因素，先识别对结果影响最大的异常值
2. **归因必须量化**：禁止"下滑明显"，必须"从 X 降到 Y，减少 Z，对总业绩影响排名第 N"
3. **动态下钻**：每一步明确"当前最值得追的异常对象是谁、下一步切哪个层级、加什么筛选器"
4. **先验证再结论**：证据不足时只写"待验证判断"
5. **建议绑定对象**：禁止"优化运营"，必须"对 XX 门店做 XX 动作"

### 3.2 下钻触发条件（满足任一必须继续下钻）
- 某单一对象贡献了该层级超过 30% 的负向变化
- 某类渠道/维度贡献了主要缺口
- 少数对象构成明显的异常集中
- 用户明确问"为什么"

### 3.3 停止下钻条件（同时满足才可停）
1. 已找到最主要异常来源
2. 已量化该来源的影响大小
3. 已定位到可执行动作的对象层
4. 已能给出针对性建议

### 3.4 归因公式三层拆解（示例）
```
公式1（结构）：TOC业绩 = 店内业绩 + 店外业绩
公式2（运营）：TOC业绩 = 店天数 × 单店单天业绩
公式3（效率）：单店单天业绩 = 客单价 × 单店单天成交笔数
```
每层拆解都要输出：本期值、对比期值、变化额、变化率、对总业绩的贡献占比。

### 3.5 表述红线
- 从高位下降但仍有规模 → 不得写"完全中断"
- 小幅波动 → 不得写"断崖式下滑"
- 单一对象异常 → 不得上升为全市场结论
- 没有直接证据 → 不得写"根因就是"

## 四、产物落盘清单

认知补充环节的产物，统一落盘到工作目录，并最终打包进产物 skill：

| 文件 | 内容 | 必需性 |
|---|---|---|
| `industry-notes.md` | 行业指标树 + 归因公式候选 + 行业术语表 | 可选（选项 A） |
| `report-insights.md` | 汇报骨架 + 指标体系 + 归因套路 | 可选（选项 B） |
| `conversation-insights.md` | 决策习惯 + 关注点 + 常用口径 | 可选（选项 C） |

这些文件最终复制进产物 skill 的 `references/`，让 agent 在每次分析时都能调用这份"业务记忆"。
